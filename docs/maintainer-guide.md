# 市场维护者手册

市场维护者负责本仓库，也负责协调各插件的开发和发布。本文是维护者的工作方法，以及从第一批插件发布中总结的经验。新加入的插件开发方读 `docs/onboarding.md` 即可。

## 一、职责

- **清单和门面**：维护 `marketplace.json`、README、`docs/onboarding.md` 和 AGENTS.md。插件开发方只能提 PR 改清单，其余文件都由维护者改。
- **接入把关**：按下文第二节的清单审核每个接入 PR，核对通过后合并，并同步更新 README 的插件表。
- **协调与纠偏**：定期检查各插件的进展，发现偏离规则就当场指出。需要所有者决定的事，汇总后一次提交，不让各方分别去问。
- **只管协调，不代写**：各插件仓库由各自的开发方负责。维护者给出规则和纠正意见，不替它们改代码。

## 二、合并接入 PR 前的检查

1. PR 只改了 `.claude-plugin/marketplace.json`，`source` 是 `{"source":"github","repo":"tealun/<仓库>","ref":"<发布分支>"}`，没有写 `version`。
2. 运行 `python3 scripts/check_marketplace.py --remote`：确认仓库公开、发布分支存在、名称不重复。
3. 运行 `claude plugin validate .`。
4. 在隔离环境里试装一次，不要动自己的配置：
   ```bash
   export HOME="$(mktemp -d)"
   claude plugin marketplace add <本仓库的本地路径>
   claude plugin install <插件名>@tealun
   ```
   装到的版本要和插件仓库最新 tag 的版本一致。
5. 合并以后更新 README 的插件表（中英文两处）。

## 三、发布插件的经验

这些都是踩过坑之后才定下的规则，新插件照着做就能少走弯路。

| 经验 | 原因 |
| --- | --- |
| 发布到任何平台之前，先把它的全部规则登记成对照表，每条要么写成本地检查，要么写明为什么不检查 | 拿平台的报错去逐条试规则，每试一次就浪费一次上传或审核 |
| 插件目录和市场都跟踪一个只由 CI 写入的发布分支，分支里只放打包好的插件 | 仓库根目录如果就是插件目录，CI、脚本和测试也会被当成插件内容扫描，报出一堆不相关的审核项 |
| `.gitattributes` 设为 `* -text` | 插件目录会校验导出内容和存储内容是否一致，换行符转换会让校验失败 |
| 仓库里不提交 zip 或 `.plugin`，安装包由发布流水线构建，附在 Release 上 | 插件目录里出现压缩包，会转人工审核 |
| README 里不写下载后直接执行的命令 | 目录会把这类命令标成风险提示 |
| 写发布分支的作业必须依赖发布作业成功（`needs: release`），不能和发布并行由同一次 tag 触发；手动补写只能从已有 Release 的 tag 来 | 并行时，发布失败的 tag 也会写进发布分支；从 main 手动触发，还会把没发布的内容送进插件目录 |
| 第三方整理的平台规则要逐条登记，结构、命名、编码这类没有数字的规则也一样 | 只挑带数字的规则做校验，会漏掉前缀、空格、换行这类会被拒的问题 |
| 版本号只以 `plugin.json` 为准，发布只靠推送 tag | 版本号散落在多处，迟早会不一致 |
| 一个仓库里有多个插件时，每个插件用一条 `plugin/<插件名>` 分支 | 一条发布分支只能放一个插件 |
| 只有技能的插件，在所有 Claude 客户端都能用；加了 MCP、hooks 或可执行脚本的插件，审核更严，也基本只能在 Claude Code 里用 | 先只发技能，等首版审核通过后再加别的组件 |
| 插件目录的第一个版本必须经过人工审核；提交后配好 GitHub push webhook（secret 只显示一次） | 不配 webhook，新版本最多要等 6 小时才会被发现 |
| 同一个仓库加文件夹只能提交一次，草稿也算；草稿的来源分支不能改 | 先把来源分支定好，再建提交 |
| 市场仓库的名字会显示在 Claude 界面上（"by 仓库名"） | 仓库名要带品牌，不要用容易被误认为官方的名字 |
| 市场只收公开仓库；商业产品不放进公开市场 | 市场从 GitHub 匿名读取；放进公开市场就等于免费公开 |

## 四、公开仓库的写作规则

- 只写对使用者和贡献者有用的内容。内部决策、会话编号、私有仓库名和商业安排都不写进文件，也不写进提交信息。
- 提交信息末尾只写 `Co-Authored-By`，不写会话链接。开 PR 时，服务端可能会在描述末尾自动加上带会话链接的页脚，开完要读回一遍，看到就删掉。
- 写进去了再删，删的只是当前文件，提交历史里还留着。要从历史里清除，就得改写历史再强制推送，而且必须先征得所有者同意。所以写之前先判断能不能公开。
- 内部的进度登记放在所有者的私有空间里，不放进任何公开仓库。

## 五、协调的做法

- 发给开发方的指令要写清楚：依据哪条规则、要改什么、哪些不要做。和之前指令冲突时，写明以哪条为准。
- 开发方说要等所有者本人确认，这是对的，维护者不要催它跳过确认，而是请所有者直接去确认。
- 开发方之间的规则冲突，由维护者统一裁定，写进本仓库的文件，然后通知所有开发方。
